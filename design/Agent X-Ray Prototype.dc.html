第3章:Agent Loop — 让模型转动起来的引擎
约 8 分钟 · 更新于 2026-08-25
本章回答一个问题:模型自己不会「连续做事」,是谁在推着它一轮轮转?答案藏在 agent-loop.ts 的一个 while 循环里。
一、循环在哪里
pi 把整个 agent 内核压缩在一个可读的循环里:只要模型还想调用工具,循环就继续;一旦它给出纯文本回答,循环自然停下。没有调度器、没有状态机——while 就是全部的控制流。
typescript
while (!stopReason) {
  const response = await callModel(messages, tools);
  if (response.toolCalls.length === 0) break;
  messages.push(await executeTools(response.toolCalls));
}
你在 Runtime 工作台里看到的每一条 before_provider_request 事件,就是这个循环转过一圈的心跳。
二、一个 turn 的解剖
一个 turn 从用户消息入队开始,依次经过四步:组装上下文 → 调用模型 → 执行工具 → 把结果写回消息队列。每一步都会向观测者扩展广播事件,所以右侧面板里 Timeline 的行序,就是这四步的真实执行序。
值得注意的是第四步:工具结果不是直接「返回给模型」,而是作为一条新消息追加进队列——模型在下一圈循环里才会看见它。这个细节决定了 pi 的会话可以在任意一圈被分叉(fork)。

namecodex-review-loop descriptionRun an independent codex code review as a fixed loop: kick off, wait, adjudicate findings one by one, re-review only the fix diff until high-severity findings are zero.
codex-review-loop
何时用
一轮实现完成、dev.ps1 test / check 全过之后、准备合并 main 之前。它只做缺陷门禁,不做设计评审;findings 指向设计缺陷时,停下回任务卡重定方案。
回路
1. 发起:改动超过 1–2 个文件带 --background,用 status / result 跟进。
2. 逐条裁定:采纳整改 / 不采纳写明理由,回填任务卡「代码审查」段。
3. 复审:只要有采纳整改的 findings 就再发一轮;第 3 轮起只审整改 diff。
bash
node <codex-companion.mjs> review --background --base <上一轮已审提交>
收口标准
不得带 high 级、或任何会丢数据 / 漏凭据 / 泄资源 / 逻辑错误的 findings 收口。低危改进项写明理由记 BACKLOG 后放行。
禁止
·以审查代替设计:在「整改 → 复审」循环里逐条堆补丁。
·非严重 findings 新增机制类修复:新队列 / 新协议 / 新抽象 / 新配置 / 新导出面。
·以「概率低」「会被替换」为由跳过整改。
